# AquaGuardians (Gangas-River) - Project Analysis & Implementation Details

This document provides a comprehensive, deep-dive analysis of the Gangas-River repository. It explains the system architecture, how the frontend and backend are structured, what features are fully integrated, and what parts of the system are simulated or "mocked" for the purpose of the Riverathon 1.0 Hackathon.

## 1. High-Level Architecture

The project is structured as a mono-repo containing two core applications:
- **Frontend**: A Modern Web Application built with **Next.js 14** (App Router), React 18, and Tailwind CSS + `shadcn/ui`.
- **Backend**: A High-performance API built with **FastAPI** (Python 3.11+).

### Core Philosophy
The platform is designed to provide a "Digital Twin" of the Ganga River, primarily relying on LiDAR terrain data to compute realistic models of flood risks and help stakeholders make decisions. The stakeholders are split into three portals:
1. **Citizens**: Mobile-first views for alerts, predicting local floods, reporting incidents, and navigating safely.
2. **Officials**: Map-driven dashboard for large-scale evacuation route planning, NGO coordination, zoning compliance, and 3D simulation.
3. **Researchers**: Data sandbox and model-tuning interface to access raw data (e.g., LiDAR arrays) and insights.

## 2. Frontend Implementation

**Path**: `./frontend`  
**Stack**: Next.js (App Router), TypeScript, Tailwind CSS, shadcn/ui.

### Key Working Features
- **Routing & State**: Employs Next.js App Router heavily (`/app/citizen`, `/app/official`, `/app/researcher`). 
- **Component Architecture**: Utilizes modular React Server & Client components. It includes a polished, fully-styled landing page using complex CSS layouts, gradients, animations, and tabbed mockups (e.g., in `PlatformOverview.tsx`).
- **Translations/Localization**: Contains a custom hook/provider (`language-context.tsx` and `translations.ts`) for multi-language support (English/Hindi context wrappers).
- **API Connectivity**: A centralized `lib/api.ts` utilizing `axios` connects to the FastAPI backend, utilizing an interceptor-based JWT authentication strategy storing tokens in `localStorage`.
- **Voice Assistant / Chatbot**: The `/api/chat/route.ts` connects live to the **Groq API** (`llama3-8b-8192`) passing a custom system prompt. This gives a functional LLM chat experience in the Citizen portal.

### Frontend Mocked Elements
- Features like SMS Alerts (`citizen/page.tsx`) have hardcoded payloads.
- Graphs and analytical charts on landing pages use procedurally hardcoded values (`height: ${h * 10}%`) rather than live rendering endpoints.
- User data and specific incident report maps fetch API data but the UI assumes the backend will populate them correctly (the backend data is largely simulated).

## 3. Backend Implementation

**Path**: `./backend`  
**Stack**: FastAPI, Pydantic, SQLAlchemy ORM, optional Celery/Redis.

The backend exposes a wide range of endpoints defined in `backend/app/api/routes` corresponding to safety checks, evacuation, reporting, and predictions. The `main.py` efficiently wires these instances using asynchronous context managers for DB initialization.

### Mocked vs Working Logic in Backend Services

Because the application requires massive government-grade LiDAR files (1.7GB TIFF files), historical databases, and real-time remote sensors, the logic features robust mock implementations specifically designed for hackathon demonstration.

#### A. LiDAR Processor (`lidar_processor.py`)
- **Intent**: Load real `*.tif` geographic datasets, calculate realistic boundaries, and read localized cell elevations using `rasterio`.
- **Mocked State**: If the `LIDAR_DATA_PATH` files are missing or `rasterio` is uninstalled, the system catches the `ImportError` / `FileNotFoundError` and gracefully falls back to `_generate_synthetic_lidar`.
  - *Simulation*: Uses Numpy trigonometric math (`np.sin()`, `np.cos()`) to generate realistic terrain grids and add artificial river valleys, noise, and base elevations.

#### B. Flood Predictor (`flood_predictor.py`)
- **Intent**: Query historical floods and utilize an AI/ML model to determine flood risk and potential disaster depth.
- **Mocked State**: The model uses logical heuristics masquerading as ML.
  - *Simulation*: 
    - Elevation Risk: Low elevation (`< 40m`) bumps arbitrary risk scores.
    - River Proximity: Computed mathematically from GPS longitude using `np.sin(longitude * 10) * 0.5 + 0.5`.
    - Historical Floods: Computed using arithmetic `(latitude - 25) * 5 % 15` instead of querying an actual database.
  - Note: There is a working dynamic `RandomForestRegressor` available inside `train_flood_model()`, but it strictly trains on the *synthetic* grid outputs generated by the LiDAR mockup to serve demonstration "feature importance" data.

#### C. Report Verifier (`report_verifier.py`)
- **Intent**: Eliminate fake reports from citizens via AI cross-verification.
- **Mocked State**: Uses basic algorithmic discrepancy checks. 
  - *Simulation*: Subtracts user-supplied smartphone `altitude` from the fetched LiDAR `elevation`. If the difference is > 50m, it deducts "confidence". If a user reports a "flood" but the LiDAR data reveals they are standing > 100m high, the system automatically flags it as fake (`UNLIKELY_FLOOD_LOCATION`).

#### D. Zone Classifier (`zone_classifier.py`)
- **Intent**: Issue policy zones for construction codes based on the risk algorithms. 
- **Working Flow**: This leverages the mock predictions from `flood_predictor.py`. Based on the outputs, it assigns Red (Zone A), Yellow (Zone B), or Green (Zone C) categories and dynamically generates restriction JSON (e.g., "construction: prohibited").

#### E. Chatbot (`chatbot.py`)
- **Working Flow**: Unlike the ML predictions, the Chatbot endpoint is fully integrated and requests real inferences from the open-source Groq API SDK using `llama3-8b-8192`.
- **Duplicate Logic**: The chat endpoint exists in *both* the Next.js `app/api/chat/route.ts` and the FastAPI `chatbot.py` indicating it might be callable from both environments directly.

## 4. Root Sandbox Scripts

The root folder contains a local machine learning script:
- `train_flood_model.py`: An independent Python script that uses `xgboost` (`XGBClassifier`) to train a real multiclass model on a local file, `historical_flood_data.csv`.
- **Usage**: It trains a model mapping features `['rainfall_mm', 'river_level_m', 'soil_moisture_idx', 'upstream_discharge_cusecs']` to `flood_risk_label` (Safe, Warning, Critical) and serializes the model to `flood_prediction_v1.pkl`. This implies future iterations intended to ditch the heuristic math in the API in favor of this serialized `joblib` model.

## 5. Summary & Verdict

**Is it working?** Yes, the infrastructure is robust, the front end is extensively built, the Next-to-FastAPI pipeline is well-designed, and the chatbot interfaces with live third-party cloud LLMs.

**Is the core domain logic mocked?** Yes. Given the complexity of hydrological analysis and massive DEM file processing, the API relies on mathematical functions to simulate terrain, synthetic heuristics to bypass genuine ML predictions in real-time mapping, and dummy datasets in the frontend code. This is a brilliant structural mockup for a demonstration that allows judges to observe speed, UX, and proof-of-concept without downloading terabytes of geographic arrays.
